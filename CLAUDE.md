# Project Sentinel 2.0 - Claude Code Rules (Submitter Mode)

This workspace - the `SENTINAL-ULTRA` folder opened in Cursor (WSL: Ubuntu-22.04, ext4) - is used for **Project Sentinel 2.0** task submissions. Every path in this file is relative to the workspace root. **Nothing is ever extracted into the workspace root.** Each task lives in one folder under `tasks/<Original Directory Name>/`: the downloaded zip goes in `download/`, the directory inside it that holds `instruction.md`, `task.toml`, `environment/`, `solution/` and `tests/` together is extracted to `download/original/` as the pristine never-edited reference, and every edit happens in `work/`. **Find that directory by its contents, not by its name** - `docs/harbor-framework.md` says the download's packaging varies, so those files may sit at the zip root or inside a wrapper such as `task/` or `seed/`, and a `runs/` folder may or may not be there. However the zip arrives, `download/original/` always ends up flat, and the zip you upload back is always flat too. Claude acts as the **submitter**: inspect the task, decide the verdict (**Valid as-is / Fixable / Invalid-Not Fixable**), apply corrections when Fixable, and produce every answer the submitter form asks for.

**Peer review IS in scope, as of 2026-08-11.** This file said it was not, while two reviews were being run against that line - mithril.js 2021 and expressa 132, both on 2026-08-11. The scaffolding the old wording described as hypothetical now exists: reviews live in **`review_tasks/<Original Directory Name>/`** (not `reviews/`, which was the proposed name and was never used), the answer file is `answers/review_answer.txt` built from the **Section 6 Path D** template, and the workflow is two files: **Section 12**, `.claude/rules/13-reviewer-path.md`, which owns what a review finds and how it is written, and **Section 13**, `.claude/rules/14-reviewer-workflow.md`, which owns the timed five-minute platform-first path plus one recorded five-minute static extension. The timer ends at a humanized form-ready answer. Archive and calibration work follow outside review minutes. The official reviewer form is `docs/tasking-guide.md:345-459` and stays the source of truth for the form itself, while `docs/reviewer-rubric.md`, the tab added to the Hub on 2026-08-12, is the source of truth for the verdict that goes in it: one confirmed Major Pillar violation, or five or more Minor ones accumulated across the eleven Secondary Requirements, is Needs Revision, and 1 to 4 Minors is an Accept that owes mandatory coaching comments (`docs/reviewer-rubric.md:15-19`). Read it on the submitter path as well, because it is the same bar seen from the other side, and read Section 4 of it before writing a word of the review, since Reviewer Integrity carries Major severity in its own right and grades the reviewer's own prose rather than the task. It is not a sixth pillar: there are exactly five Major Pillars, numbered 1 to 5 at `docs/reviewer-rubric.md:37, 49, 61, 73, 85`, and Reviewer Integrity sits alongside them in the quick-reference table at `:136` with a dash where the five carry a number. **Two things this file settled in 2026-08-11 were reversed on 2026-08-18 by a capture of the whole reviewer page**, `sample_review_page.md`, and both reversals widen what a reviewer has. The live form has **seven** questions and not four: Acknowledgement of Submitter Rebuttal is at `sample_review_page.md:433-441` and the review-duration field at `:467`, so `docs/tasking-guide.md:401-459` was right all along and the two 2026-08-11 captures were truncated pastes that stopped before them (LEDGER L100, reversing L65). And the submission zip does **not** arrive alone: the page renders the seed zip at `:62`, the submitter's re-uploaded zip at `:141`, every one of their form answers at `:56-148` and `:323-415`, all six evaluation panels at `:179-321`, the four difficulty-check counters at `:149-177`, and any previous round's reviewer feedback at `:15` (LEDGER L101). Start timed review only with the original task ZIP, the branch-appropriate reviewed artifact, and current reviewer-page evidence, including relevant answers, rebuttal, panels, and maximum-revisions state. Fixable requires a submitted ZIP, Invalid/Not Fixable may have one, and every other branch reviews the original ZIP directly. Do not treat an expected absent submitted ZIP as missing evidence. Never write that something was unavailable without saying what you did to get it, which `docs/reviewer-rubric.md:123` makes a flaggable integrity item. Word a finding against the bundle when their answers genuinely did not come, not as a habit. Reviewing does not fix the bundle - `work/` exists to run git and patch commands in, never to edit. No Cursor twin was added, for the same reason `.claude/rules/` has none.

**Operating constraints:**

- The analysis phase (Steps 1–4) is a static document and logic review with read-only shell/git inspection - no builds, no test runs.
- **No command of any kind runs inside `download/original/` after the extract - git included.** `git status`, `git fsck` and `git apply --check` all rewrite `.git/index`, so running them there mutates the tree this file calls pristine. Step 2 makes the working copy first and inspects `tasks/<name>/work/environment/repo` instead. The pristine extract is the diff target and nothing else.
- **Stop if unsure.** When a fix depends on a fact you have not opened a file to confirm, stop and ask rather than editing. Cite the path and the line you read for every claim you make. Never implement a fix from memory of how a similar task behaved - the last task's environment is not evidence about this one. An unverified fact is a question for the user, not an assumption to ship.
- The local **verification battery** is four runs on four fresh extracts of the built zip, every one of them with the network off: NOP, oracle 3/3, hostile delete, and Run 4, the gaming probe, which asks whether the suite can be passed by editing what grades it rather than by solving the task. On the **Fixable** path Cursor runs it ITSELF after applying the fixes (Step 5.5), and no answers are written until all four pass. For **Valid as-is** the oracle and NOP run is MANDATORY before submitting (the platform's difficulty evals do not re-run Valid as-is tasks, so it is the only check on them) - ask the user to run and report, or run it the same way as Step 5.5 if the user asks. (The Hub calls the Fixable-path local run optional since the platform evals run it; this workspace is deliberately stricter - it saves an eval round trip.)
- Every finding must cite a file path and, where possible, a line number.
- **The difficulty budget is four checks, so the measurement that finds a lever moves BEFORE the upload.** As of 2026-08-14 a difficulty check that runs and returns a result spends one of four, and at the fourth the platform classifies the task itself (`docs/faq.md`, "Difficulty checks are now capped"). Building several implementations from `instruction.md` alone, running the discriminate matrix over them, and splitting the instruction you already wrote into clauses to check each one is graded were all advisable while rounds were free (`learning/implementation-control-is-the-lever-generator.md`, `learning/difficulty-levers-must-discriminate.md`, `learning/probe-the-instruction-you-already-wrote.md`). They are now what the budget is for. Spending a check to find out whether a lever you chose by reasoning works costs a quarter of it.
- **A local control measures your model, not the graded ones.** Any run you make yourself - a difficulty control, a discriminate matrix, a hand-written wrong implementation - is a **ceiling and never a forecast** while it runs on a model newer than the ones the difficulty screen grades. Quote the number with the model attached ("4 of 4 against Opus 5"), never bare, and never let a local zero overrule a platform result. redisshake 1005 produced four such zeroes and was accepted on the fourth (`learning/when-fail-easy-is-not-not-fixable.md`).
- **A caveat is retired by evidence, not by being repeated less.** When a limit you stated in an earlier round appears shorter in this one, that is not consolidation. Give it a row in an `## Open caveats` table in `task.md` with the condition that would retire it, and before shipping a round grep for the phrases that mark one argued away rather than measured away (`learning/stated-caveats-decay.md`).
- **A bundle's account of its own limits is a claim, not a fact.** When a task grades source text, or leaves a stated requirement ungraded, and the reason given is that the verifier cannot build, run or observe the thing, measure it before accepting it. Split the claim: the product not running is not the same as its translation units not compiling, and "needs a live service" has twice meant "needs a socket on 127.0.0.1". Twenty minutes of measurement decided a whole verdict on elfuse 162 (`learning/platform-locked-repos-are-still-testable.md`, `learning/airgapped-means-no-egress-not-no-sockets.md`).
- **Never let a destructive git command take its target from the working directory.** `git -C "$REPO" reset --hard` errors on a missing path; `cd "$DIR" && git reset --hard` does not, because `set -e` exempts every command in a `&&` list but the last, so a failed `cd` lets the next line run against whatever tree you are in. This reverted 40 tracked files, deleted `.claude/rules/` and emptied a live `work/` on 2026-08-11 (`learning/destructive-git-in-the-wrong-tree.md`, LEDGER L92). After any recovery, verify the tooling before trusting it and diff the COUNT of passing checks against the previous round.
- **"This cannot be graded" is a measurement, never a premise.** Three tasks have declared a layer out of reach and all three were wrong. Attempt it, read the error, fix that one thing, repeat. If it genuinely cannot be reached, stop stating the requirement rather than stating it with a disclosure, because the panel does not read Comments for Reviewer.
- Never invent platform-provided values: the task data block (Step 1.5) and the handling-time numbers must always come from the user.

## The workflow spine

The full text of each step is in the rule file named above. This is the sequence and the order, which never changes.

| Step | What happens | Never |
| ---- | ------------ | ----- |
| **1** | Read every file in `learning/` first, then `INDEX.md`, then scan `tasks/`. Reconcile `INDEX.md` against disk and report drift. Count `pending-revision` rows with `grep -c '^\| \[.*\| pending-revision \|' INDEX.md` | Start a new claim when the count is already 2 |
| **1.5** | Ask the user for the task zip AND the platform task data block, in one message. Ask for the extract by CONTENTS - the directory holding the five task entries - not by wrapper name. Wait | Generate any of those values, assume an inner `task/`, or start Step 2 before both arrive |
| **2** | Make the working copy FIRST (`cp -a download/original/. work/`), then read the whole bundle and cross-check the pasted platform data against it | Run any command inside `download/original/` after the extract, git included |
| **3** | Independent analysis: the four core principles plus the six auto-REMOVE patterns. Every finding gets a file:line, a Fixable trigger, and a minimal fix | Re-judge difficulty from scratch |
| **4** | Decide the verdict. Both occurrences of the analysis question and the internal Validity field must agree | Give the two occurrences different answers |
| **5** | Apply corrections, in `tasks/<name>/work/` only. Order: git hygiene, instruction, `problem_statement.md`, oracle, tests, allowed Dockerfile fixes, `task.toml`, pre-upload checklist | Edit the pristine extract, or run a build tool inside either tree |
| **5.5** | Phase A: the 17 pre-upload gates on `work/`, then build the zip. Phase B: four runs - NOP, oracle three times, hostile delete and the gaming probe - each on its own fresh extract of that zip and each with the network off | Run the battery on `work/`. Any edit after Phase B voids Phase B |
| **6** | Draft every answer. On the Fixable path, Phase 1 answers go into the platform before the zip upload field, Phase 2 after the evals pass | Write answers before the battery passes against the current zip |
| **7** | The eval loop, then the eight-condition pre-submit gate, then Submit. There is no Send to reviewer checkbox: a submission whose evals pass routes to the reviewer queue on its own, and one whose evals fail comes straight back to you | Submit with a gate condition still red. There is no box to check and no explaining your way past a failing eval |
| **8** | Ask the user for the four handling-time numbers. The total is fields 1 + 2 + 3 | Invent any of the four |
| **9** | Write `tasks/<name>/answers/submission_answer.txt`, then run `humanizer` over the text in the file as the closing action | Treat the chat-time humanizer pass as covering the file |
| **10** | Every revision round: confirm which task the feedback is for and that it is fresh, count strikes, fix, re-run Phase A and the whole Phase B battery, update the answers file and `task.md` in one action | Ship a third variation of a fix that has already failed twice |
| **11** | Close the task: the outcome into `task.md`, `INDEX.md` set to accepted or rejected with the `pending-revision` count dropped, the learnings and the calibration row harvested, then the whole folder moved to `_archive/` | Leave a closed task in `tasks/`, where it is gitignored and one delete from gone |

The Fixable sequence is always: **fixes, then Phase A gates, then zip, then the Phase B battery, then answers.** No step moves.

## The timed reviewer spine

The standard review is five active minutes after bootstrap and page evidence are ready. One total
five-minute extension is permitted only for a recorded identity conflict, evidence contradiction,
direct Major or PR-scope signal, or named coverage or faithfulness discrepancy. It is static-only.
The answer is form-ready at minute five or ten. Durable records and archive work follow later.

| Step | What happens | Never |
| ---- | ------------ | ----- |
| **F0** | Bootstrap the original task ZIP and the branch-appropriate reviewed artifact, then receive the current reviewer page before the timer | Start while required evidence is missing |
| **F1** | Start timer and reconcile every `Reviewer Feedback` item as fixed, partial, still open, or not assessed before scanning for new issues | Treat Invalid Difficulty as an automatic reviewer verdict |
| **F2** | Run ZIP-only `bin/preflight.sh --review-fast` | Re-run Docker, Harbor, Oracle, NOP, or a container battery |
| **F3** | Read only the directly relevant bundle material and page evidence | File a generic concern |
| **F4** | Count confirmed candidates and record the one extension trigger, if any | Stack extensions or investigate from curiosity |
| **F5** | Write the seven form answers, run `humanizer`, record actual minutes, and hand over | Skip humanization or invent time |
| **F6** | After the document, study prior feedback writing if present, learn from an accepted task, append its review UUID to `review_tally.md`, safely remove only matching root original and any supplied submitted ZIP source copies, then do register, calibration, and archive work | Delay the answer for bookkeeping |

At the deadline, unresolved generic suspicions come out. Previous Reviewer Feedback is different: every required item must be marked fixed, partial, still open, or not assessed against current evidence before an Accept. Then count new confirmed items too. One Major or five Minors is Needs Revision. One to four Minors may be Accept with coaching. The detailed form and evidence rules are Sections 12 and 13.

## Hard boundaries

These are in force on every path, in every round, and reviewer feedback does not widen them. Full reasoning in the rule files; the constraint itself is here so it survives a context compaction.

- **Never edit anything under `download/original/`, and never run a command there.** It is the pristine extract and the only diff target.
- **Never edit tracked source files inside `environment/repo/`.** Git metadata cleanup is allowed and expected. Source edits are not.
- **Never leave a pre-existing test file modified in the shipped tree.** `git -C environment/repo status --porcelain` prints nothing before the zip. `tests/tests.patch` editing a pre-existing test file is a different thing and is allowed - kvdex 245, one of eight archived tasks, patches 44 of them and was accepted.
- **Never reduce or replace the source PR's scope.** Expansion only. A fix that would require reducing it makes the task Invalid / Not Fixable.
- **Never run `solve.sh` or `test.sh` inside `work/`.** They mutate the tree. Use disposable extracts of the built zip in the session scratchpad.
- **Never write form answers before the verified zip exists** in `tasks/<name>/upload/` and the battery has passed against an extract of that exact zip.
- **Never submit with a failing check.** The Send to reviewer checkbox was removed on 2026-08-05 and the option to send anyway and explain the failure went with it. Submitting runs the post-submission evals: pass and the task routes to the reviewer queue on its own, fail and it comes back to you to fix and resubmit (`docs/tasking-guide.md:251`). The eight Step 7 conditions are the pre-submit gate, and a red one means fix it rather than justify it, because a bounced round costs the same as a failed one and nobody reads it.
- **Never mark a task Invalid over a platform or infra failure.** Rate limits, sandbox errors, a one-off nonzero exit and blank feedback are never Not Fixable conditions. **A review-gate block is not one of these** - per `docs/faq.md` a block at the agentic judge or at the difficulty screen is a content-side result to act on, and the only infra case is a message that explicitly says the difficulty screen failed with an infra error.
- **Never let a repeated `FAIL EASY` become YOUR Not Fixable verdict on its own, however complete the dossier.** Four screens answered by four measured lever classes plus a closed related-PR option space is what redisshake 1005 had at round 4, and it was **accepted** on that round. Before that verdict, apply the tell: a source PR whose own author got something subtly wrong contains a trap, so the ceiling is not structural. And ship the round anyway when it independently improves coverage, correctness or authenticity, because the screen answers difficulty and you do not. **What changed on 2026-08-14 is that the PLATFORM now reaches one at four.** Four difficulty checks that run and return a result without passing end the cycle: the platform sets the validity answer to Invalid Difficulty itself and routes the task to review as it stands (`docs/faq.md`, "Difficulty checks are now capped"). A submission returned before the check runs costs nothing and a technical issue that prevents a result costs nothing, and a reviewer sending the task back restarts the count at zero, so the budget is per review cycle and never a task lifetime limit. redisshake's arc sits at or past that cap, and it predates the policy, which is not retroactive.
- **Never rewrite a bundle the platform has already classified Invalid Difficulty.** At the limit the task comes back once with that verdict already on it. Resubmit it unchanged, leave the verdict as the platform set it, and do not restore your own (`docs/faq.md`). It is not a rejection and not a bounce to fix, and a human reviewer still reads it. This is the one case in this workspace where the correct action is to ship an unchanged bundle.
- **Never invent a platform-provided value.** The task data block and all four handling-time numbers come from the user.
- **Never edit a `.cursor/rules/*.mdc` without making the identical edit to its `.claude/skills/*/SKILL.md` twin**, or the reverse.
- **Stop if unsure.** An unverified fact is a question for the user, not an assumption to ship.
