## 4. Evals and the Quality Check (Fixable path)

### The loop

- **Pre-upload answers first:** the analysis verdict (both occurrences + [Internal] Validity), where-issues, what-issues, and the numbered issue details sit above the upload field - enter them before uploading the zip for Check feedback
- **Static Checks** ("Check feedback"): instant structure + Dockerfile validation. Must pass for the task to be eligible for submission. The build runs its phases in order and stops at the first failure, so problems surface one at a time - a green static check only means the _next_ phase can now run (verified - see `learning/static-checks.md`)
- **Prescriptiveness check** (`cdg_sentinel_ultra.prescriptiveness`): scores `instruction.md` 0–1 and lists findings with severity and rule numbers. It fails the BUILD phase but is explicitly non-blocking for submission ("please address the findings before sending the task to review"). Two rules do the work - Rule 3 catches naming the library or built-in to use (`node:v8`, `node:zlib`), Rule 2 catches naming internal file paths or where existing code lives today (`src/utils.ts`). Public surface is fine: module trees, `mod.ts` barrels, required symbol names, type shapes and export-map entries all pass. **Before deleting any path or name from the instruction to satisfy this check, grep the tests for it** - if a test depends on it, repoint the test at something the instruction still states, or you trade a non-blocking finding for a blocking `test_faithfulness` one. Full detail in `learning/prescriptiveness-check.md`. **This bullet is about the build-phase score only.** Instruction quality has a separate blocking path through the Quality Check's must-have `criterion: Instructions` items - see `learning/quality-check-criteria.md` and the rubric-panel section below. Non-blocking here never means instruction quality is advisory
- After the bundle runs, read-only summaries populate. This file and `docs/tasking-guide.md:241-245` both say **three** and the live page shows a **Submission Feedback** section carrying **seven** fields, measured 2026-08-18: Static Checks (`sample_review_page.md:181`), Prescriptiveness (`:187`), Download difficulty check results (`:193`), **Difficulty Check** (`:199`), **Agentic Judge Quality Report** (`:237`), **Oracle Check** (`:277`) and **Quality Check** (`:299`). Four of those are result panels and the Agentic Judge Quality Report is its own field sitting **between** Difficulty Check and Oracle Check, not inside it. The three named here are still the three that carry a verdict, so nothing below changes: **Difficulty Check** (agent simulation + verifier stats), **Oracle Check** (golden solution vs verifiers), **Quality Check** (blocking rubric-panel judge). This Difficulty Check is not the review gate's difficulty screen and not the post-acceptance rollout either - see the review gate section below before quoting one as the other. **Download the difficulty results artifact** - it carries the platform-side verifier stdout, and asking for it is the first action on any failed check (Step 10 item 1), above local reproduction in the evidence hierarchy. **On a review-gate block at the agentic judge there is a second thing to ask for and the artifact is not it** - the reasons sit in the "Agentic Judge Quality Report" field on the submission, collapsed and marked optional lower down the form (`docs/faq.md`, "My eval says Review gate blocked at the agentic judge / difficulty screen"). Ask for both. The artifact carries verifier stdout, the report carries the judge's verdict and the axes and files it cites
- **Oracle Check: the bar is 3/3.** The platform runs the golden solution **three times** and anything below 3/3 blocks the submission. On the Fixable path a sub-3/3 result is a task defect, not flake. Read the number before theorising, because `0/3`, `1/3` and `2/3` are different failures:
  - **1/3 or 2/3** - run one passed and a later one did not, so state accumulated between runs. Reproduce it by running `solve.sh` twice in one local container. A reverse-apply fallback in `solve.sh` is the classic cause
  - **0/3** - run one already failed, which rules out every state-accumulation theory in a single step. Do not go looking at idempotency; the first invocation is broken
  - **Task defect vs infra:** real per-test output alongside an `N/3` line means task defect. Blank or null results with no verifier output at all means infra. See the "Why this was NOT the 0/3" section of `learning/solve-sh-idempotency.md`, where a correct fix to a genuine idempotency defect was shipped against a `0/3` that arithmetic had already ruled it out of
- **Submit only once every condition in the Step 7 pre-submit gate is green** - Static Checks, Difficulty with zero invalid trials, Oracle 3/3, Quality Check including the must-have criteria, Instruction Sufficiency not FAIL, the Step 5.5 battery against the current zip, the zip newer than `work/`, and the upload-ledger row written. **There is no "Send to reviewer" checkbox and no way to force a task past a failing eval** - the box was removed on 2026-08-05 and the `AlwaysNoPass` message went with it (`docs/tasking-guide.md:251`). Submitting runs the post-submission evals on their own: they pass and the task goes straight to the reviewer queue, they fail and it comes back to you to fix and resubmit. **Submitting is still not the same as reaching a person.** The review gate runs before a reviewer sees it either way (section below), and a gate block comes back to you as an eval result to work like any other failing check
- **Needs Revision notes may cite a Guidelines section.** Reviewer form question 4 now asks reviewers to cite the relevant section of the Guidelines where it helps - not for every point, but for specific or easily-missed rules (`docs/tasking-guide.md`, reviewer form, "If Needs Revision"). When a finding carries one, open that section in `docs/guidelines.md` before deciding what the finding means; it is the fastest route to what is actually being asked for. Absence of a citation says nothing, since it was never required
- In-app checks have a **5-minute runtime limit** - run and iterate on them until they pass, and only then submit (`docs/tasking-guide.md:253`)
- Protocol when checks fail: read the summaries and the logs, revise within the editing rules, re-upload and re-run the evals, and repeat until they pass. A passing submission is sent to the reviewer automatically (`docs/tasking-guide.md:262`)
- **Two strikes on the same failure.** That loop assumes each round teaches you something. When a fix you verified locally comes back failing a **second** time, it is not teaching you anything and the next variation will not either. Stop refining the theory and remove the dependency instead. A local reproduction proves a condition is *sufficient* to cause the symptom, never that it is the one the platform is applying, so a third locally-verified hypothesis is the same trap wearing a new hat. Read the round-over-round trend as evidence in its own right: a number that does not move across two different fixes means neither fix touched the cause. kvdex 245 went 13 of 16 invalid, then 16 of 16, then 15 of 16, on three correct fixes to three genuine defects, none of which was the defect. Full protocol and the evidence hierarchy in `learning/diagnosing-platform-only-failures.md`
- **A harness failure voids the whole round.** `invalid trial` / `harness failure` is not one bad result among several: when trials are scored invalid you learn nothing about difficulty, nothing about the quality panel's test axes, and nothing about agent behaviour, so every other check that ran becomes uninformative. Budget diagnosis accordingly. The choice is not "an hour of diagnosis or ship now", it is "an hour of diagnosis or a whole round that teaches you nothing", and a round that teaches you nothing now comes straight back to you unread
- **A difficulty check is a budgeted resource as of 2026-08-14.** Four difficulty checks that run and return a result **without passing** end the cycle: the platform sets the answer to the validity question to **Invalid Difficulty** itself and sends the task to review as it stands (`docs/faq.md`, "Difficulty checks are now capped - what is Invalid Difficulty?"). A reviewer sending the task back restarts the count at zero, so it is four per review cycle and not four for the life of the task. Read the **Difficulty checks run** and **Difficulty checks remaining** fields on the submission before deciding what the next upload is for. Full treatment in the budget section below
- Throughput rule: no daily task cap, but at most **two tasks in "pending revision" at once** - the platform blocks a new claim until one clears

### The review gate (runs with the evals, before a reviewer sees the task)

A two-stage check that stands between your bundle and a human reviewer: the **agentic judge** first, then a **difficulty screen**, a cheap single-arm rollout. The second stage only runs if the first passed, so the block always names the stage that stopped it (`docs/faq.md`, "My eval says Review gate blocked at the agentic judge / difficulty screen"). **A block is a real content-side result to act on, not an infra failure** - the single infra case is in the troubleshooting list below.

**One thing that capture does NOT settle, so the claim below stands as written.** The judge status on that page is `OK` (`sample_review_page.md:273`), so it says nothing about where a **block** prints. The paragraph below says a gate block prints inside the `## Difficulty Check` panel and that no fourth panel appears; the existence of a separate Agentic Judge Quality Report **field** does not refute it, because a field that exists when the judge passes is not evidence about where its block text lands. Treat the placement claim as untested rather than refuted, and settle it the next time a block comes back.

**Where it reports, measured on this workspace's own rounds.** `docs/faq.md` says the gate runs "before your task reaches a reviewer" and does not say when it fires. This workspace has the platform text for two of them, in the `revision.md` at the **workspace root** (not the older `chat_transcripts/` file of the same name, which is a different paste with different line numbers). Both arrived as ordinary eval results in the Step 7 loop rather than after the task was submitted: AltBeacon 1177 (root `revision.md:113`, `Evaluation FAILED. Review gate blocked at the agentic judge`) and libcrux 1165 (root `revision.md:393`, blocked at the difficulty screen). In both, the gate's output is printed **inside the `## Difficulty Check` panel** - it is that panel's current content, not a fourth summary next to it. Do not wait until you have submitted to see a gate result, and do not expect a separate panel to appear.

| Summary line | What it means | What to do |
|---|---|---|
| Blocked at the agentic judge | The judge returned a needs-work verdict. The one-line eval summary names only the stage, never the reasons | Ask the submitter to expand the **"Agentic Judge Quality Report"** field on the submission - it is collapsed and marked optional, lower down the form. It carries the DISCUSS / REMOVE status and cites the specific axes and files. Fix what it names, then resubmit |
| Blocked at the difficulty screen (cheap single-arm rollout) | The screen found the task **trivially easy** - the model solved every attempt | **Ask for the results artifact first, by name.** A screen block DOES produce one, measured on statrs 315: `logs_artifact.zip`, 199 files, carrying every trial's `agent/trajectory.json`, `verifier/report.json` and `verifier/test-stdout.txt`. It is the top of the evidence hierarchy here, and `Task Instruction Sufficiency: NOT_APPLICABLE, debug output not available` is a line INSIDE it, not proof it is absent. Read the FAILING trial's transcript, because it names the lever class. Then raise difficulty, and note that **expanding PR scope is not automatically the answer** - one whole extra feature converted zero of eight agents on statrs 315 (`difficulty-is-divergence-not-volume.md`). Never hand-edit the `task.toml` difficulty or pass-rate fields. **Then read `Difficulty checks run` and `Difficulty checks remaining` before choosing what the next upload carries** - the FAQ caps difficulty checks and never says whether this cheap single-arm screen is one of them, so do not assume the screen is free and do not book it as spent either. Those two fields settle it the first time a screen block comes back, and at four non-passing checks the platform writes Invalid Difficulty itself (the budget section below) |
| Not run: difficulty screen | The judge blocked first, so the second stage never ran | Nothing. It is expected, not a second error |

**The review gate's difficulty screen is NOT the task's final difficulty grade.** `docs/faq.md` says the full difficulty rollout is a separate check that runs later, after a reviewer accepts. So two different difficulty results are in play and they are not interchangeable: the cheap single-arm screen you see now, and the full rollout you never see until the task is through review. A screen that says EASY is a gate result, not the grade.

**The `## Difficulty Check` panel does not always mean the same thing, so read its shape before quoting it.** The same panel carried a full multi-trial report on the earlier rounds recorded here - 8 trials per model, per-model invalid counts, `Difficulty: PASS HARD` (root `revision.md:77`) - and carries review-gate output on the later ones (root `revision.md:115` and `:395`). A round-over-round comparison that reads a single-arm screen against an 8-trial run is comparing two different measurements. Say which shape a number came from whenever you cite one.

**One block is a task result. A cluster may not be.** The same review-gate block repeating across different tasks, or several in a short window with otherwise clean checks, can indicate a platform-side problem. Have the user flag that on Slack with the UIDs (`docs/faq.md`, same question). One block on one task is not a cluster and gets worked as a content defect.

### The difficulty check budget and the Invalid Difficulty verdict (new 2026-08-14)

**A task gets four difficulty checks, and the fourth one ends the cycle whatever you think of the bundle.** `docs/faq.md`, "Difficulty checks are now capped - what is Invalid Difficulty?", says that before 2026-08-14 a task could cycle through the difficulty check with no limit, and that as of 2026-08-14, once four difficulty checks have run on a task without passing, the platform classifies it **Invalid Difficulty** and sends it to review as it stands. It is not a rejection, it does not apply retroactively to earlier tasks, and a human reviewer still reads the result. Nobody in this workspace has hit the cap on a real run yet, so everything in this section is documented policy read off that FAQ entry rather than something measured here, and the sentences below say which are readings.

**What spends a check.** The counter only increases when a difficulty check **runs and returns a result**, and that is the whole rule. A submission that comes back to you before the check runs costs nothing. A technical issue that prevents a result costs nothing, which is the same infra carve-out the troubleshooting list below already makes, seen from the budget's side: a crash that produced no verdict produced no charge. That last clause is a direct reading of the FAQ sentence and not a measurement. **And a reviewer sending the task back restarts the count at zero**, so the cap is per review cycle rather than per task lifetime. Do not write it or plan around it as four checks for the life of the task.

**Read the counter before you decide what the next upload is for.** The release adds four read-only fields to the submission. The FAQ names two and a capture of the live page on 2026-08-18 named all four (`sample_review_page.md:149-177`): **Difficulty checks run**, **Difficulty checks remaining**, **Last counted submission version** and **Last difficulty check result**. Two of the readings below stop being readings because of their helper text. `Difficulty checks run` is described as counting runs "**since the last review**", which is the platform stating the per-review-cycle reset this file inferred. And `Last counted submission version` is "the submission version id the last increment was charged to, which is what makes a platform retry of the evaluation cost no run", which is the mechanism behind the carve-out for a check that produced no verdict. The full table is in Section 2. The two named in the FAQ are still the two you read first: **Difficulty checks run** and **Difficulty checks remaining**. Ask the user for both in the same message that carries a difficulty result, the way Step 10 already asks for the results artifact, and put them in the round record in `task.md`. They are the only place the budget is visible, and they are what settles the readings in this section that no amount of re-reading `docs/` can: if a round you believed was free moves `Difficulty checks run`, the reading was wrong and the number is right. One thing the FAQ does not separate, so treat it as open: it says "difficulty check" throughout and never distinguishes the `## Difficulty Check` panel's multi-trial run from the review gate's cheap single-arm screen, and this file already says the same panel carries both shapes. Do not assume the screen is free. The two counter fields answer it the first time a screen block comes back.

**At the limit the platform writes the verdict, and the correct action is to resubmit an unchanged bundle.** `docs/faq.md` says the platform automatically changes your answer on the validity question to Invalid Difficulty, that the task returns to you once with that verdict already on it, and that you submit it again for review without changing anything and leave the verdict as set. This is the one case in this workspace where a task coming back is not a bounce to fix. Do not rewrite the bundle, do not restore your own verdict, do not open a revision round against it, and since the instruction is to change nothing, leave the form answers alone as well. Record the outcome in `task.md`, which is workspace bookkeeping and never part of the submission.

**Invalid Difficulty is the platform's verdict and it is not yours.** The cap changes what the platform does after four checks and changes nothing about your own verdict discipline. A repeated `FAIL EASY` still does not entitle you to reach Unfixable - Difficulty yourself, and both caveats behind that rule stand: ask first whether the source PR's own author got something subtly wrong, because a trap upstream means the ceiling is not structural, and remember that a local control runs on a newer model than the screen grades, so it is a ceiling and never a forecast (Section 3, `learning/when-fail-easy-is-not-not-fixable.md`).

**Two things the release did not do, recorded here once rather than everywhere.** `docs/tasking-guide.md` was not updated: its list of answers to the validity question still shows the three this workspace has always worked to (Valid as-is, Fixable, Invalid/Not Fixable) and does not carry Invalid Difficulty as an option, even though the FAQ says the platform writes that value into that question. The Hub's Changelog tab was not updated either. **The form itself did carry it all along**, seen 2026-08-18 at `sample_review_page.md:69`, `:79` and `:93`, worded "Invalid Difficulty (Difficulty runs have been exhausted and task is auto marked as invalid)" and sitting in the same radio as the other three including the internal Validity field. So the drift is in `docs/` rather than a gap between `docs/` and the platform, and it is flagged rather than resolved here. What has not changed is who picks it: the platform sets it at the cap, and the Last-difficulty-check-result field exists precisely so the platform can re-apply its verdict if an EC moves the radio back.

**The rerun ladder is no longer free, and that is a reading.** `learning/platform-announcements.md` carries a difficulty rerun ladder that says to rerun a failed Difficulty Check once, then a second time, before diagnosing anything. Read against the FAQ sentence above, every one of those reruns that returns a result spends a check, so a ladder taken to its second rung has spent half the budget before diagnosis starts. That is a reading of the documented sentence and not something measured here, and the counter fields settle it in a single round. Until they do, lean on the exclusion the ladder already carries: it says not to rerun a screen reporting the task trivially easy, because that result is a measurement rather than noise, and that is exactly the block this section is about.

**A repeated `FAIL EASY` terminates now, and the two-strikes rule still does not apply to it the way it looks like it should.** Until 2026-08-14 this passage read that a repeated `FAIL EASY` does not terminate and that the count does not force a verdict, which was true for as long as the difficulty check could cycle without limit. It is superseded: the fourth check that runs and returns a result without passing ends the cycle with the platform's own Invalid Difficulty verdict. What the cap does not touch is the reasoning underneath. Two strikes tells you to stop refining *one theory* and remove the dependency, and four screens answered with four genuinely different lever classes is four theories rather than four variations of one, so the strike table still gets a row per class. What changed is that you no longer get unlimited attempts to work through those theories, and the cycle now ends whether or not you have worked through them.

**Measured: redisshake 1005 went through four `FAIL EASY` screens, four lever classes each measured at 0 of 4 against a local control, and was ACCEPTED on round 4.** That arc sits at or past the cap. The record says the screen blocked four times and does not say how many difficulty checks ran in total, so do not quote it as exactly four checks. It also predates 2026-08-14 and the policy is not retroactive, so it was not affected by any of this. Its lesson is not withdrawn: a complete Not Fixable dossier is not a Not Fixable verdict, and the round that improves the bundle is worth shipping even when its lever is unmeasured. What the cap changes is that the same demonstration now has four checks to land in rather than as many as it takes. Four things follow, and the first one is where the budget goes:

- **Do the measurement before the upload, because that is what the budget is for.** Generate three or four implementations of the feature from `instruction.md` alone, blind to the oracle, the tests and the upstream commit, then run the graded suite against each. It settles whether anything in the suite discriminates at all, whether the suite is overfitted, and where the lever is: make each one report what it was unsure about and the overlap between those reports is a ranked list of candidates written by something that just did the task. Then run the discriminate matrix over the candidates and discard every row where the honest implementations agree (`learning/difficulty-levers-must-discriminate.md`), and split the instruction you already shipped into clauses and check a test fails when each one is violated (`learning/probe-the-instruction-you-already-wrote.md`). All three were advisable when rounds were free and are now the thing standing between you and a check spent on a guess, because **a lever chosen by reasoning and tested by uploading costs a quarter of the budget to disprove.** On ziti-sdk-c 668 rounds 4 and 5 chose levers by reasoning and both measured zero, and round 6 ran this first, found four for four at 26 of 26, took the lever from three matching honest-gaps reports, and was accepted. **Also read the `Unit Tests Results` block before the headline** - it counts agent runs only, so the pass count against the run count separates real failures from runs that never reached a test (`learning/implementation-control-is-the-lever-generator.md`, `learning/difficulty-screen-unit-table.md`)
- **Ship the round anyway when it independently improves the bundle.** Round 4 there was uploaded on the stated reasoning that it grades a path nothing had graded, merges padding without losing an assertion, and fixes a second documented upstream defect - all true whatever the screen said. That is the reasoning that got the task accepted. The screen answers difficulty; your job is whether this bundle is more correct, better covered and more authentic than the last one
- **Your local control is a ceiling.** It runs on a newer model than the screen grades, so an all-pass tells you the lever *might* be worth nothing and never that it is. Write the model into the number. redisshake's own artifact showed gpt-5.5 losing seven graded assertions to a trap the local control found 16 times out of 16 (LEDGER L35, L51)
- **Try the cheapest lever class first.** Of the four classes measured there, the one that actually bit on the platform was **withholding a stated answer from `instruction.md`** - no scope, no id budget, no reviewer risk. Withhold a fact when its natural wrong reading is *silent* (compiles, runs, looks plausible); state it when the wrong reading fails loudly on the first byte, because that is a debugging speed bump and not difficulty. See `learning/difficulty-levers-must-discriminate.md` for the class catalogue and `learning/when-fail-easy-is-not-not-fixable.md` for the whole arc

### Troubleshooting known failures

- **"0/8 valid trials - infra/harness failure"** or **"tests.patch did not apply"**: check the base-commit apply first (`git apply --check`), but if that already passes, the cause is almost certainly that an **agent edited or created a file `tests.patch` also touches**. Guaranteed on an API migration, since the visible tests stop compiling and the agent fixes them, and just as likely on a feature task where the agent writes its own test for the class it was asked to build. A clean oracle run never catches it. Fix it in `tests/test.sh` by restoring the test tree immediately before applying the patch, and **do not build that restore on git** - see Section 10.3 for the two shapes that work (create-only patch, or a base64 payload embedded in `test.sh`) and the one-liner that tells you which. Three git-based restores shipped on kvdex 245 across three rounds and none of them measurably worked, because the verify-time workspace is not a git repository; the git-independent one was accepted first time. Verified - see `learning/tests-patch-vs-agent-edits.md`. Other causes: a broken repo (dropped `.git/refs/` from a bad zip), or missing tmux/asciinema/bash in the image
- **`Task Instruction Sufficiency: FAIL`**: the signature is agents at **0%** with module-not-found, import or unresolved-symbol errors while the **oracle passes 100%**. That combination says a fail-to-pass test imports a name the instruction no longer declares as a deliverable - the oracle knows the name because the golden patch creates it, and no agent can, because nothing told them to build it. It is what you get after stripping a path or a symbol from `instruction.md` to satisfy a Q9 or prescriptiveness finding while a graded test still depends on it, which is the exact trade the prescriptiveness bullet above warns about from the other direction. **The fix is to re-anchor the graded ids onto symbols the instruction still names as deliverables, not to put the path back** - restoring it re-opens the Q9 finding and you loop. Do not submit while Sufficiency reads FAIL, however green the other panels look. See `learning/prescriptiveness-check.md`. Distinguish this from `NOT_APPLICABLE`, which only means the harness did not evaluate sufficiency on this run and is not a result
- **Agent timeout**: raise `[agent] timeout_sec` up to the 7200 max. If it still times out, open `runs/` to see WHERE the time went - usually one slow step, not the whole task. If it genuinely cannot fit in 7200 and the only remedy would be shrinking the PR, the task is Not Fixable
- **Nonzero exit-code agent error**: work the usual checks first (local Docker build, tests.patch applies to base, agent timeout, `network_mode` per block). If it persists, remove the `curl` package install from `environment/Dockerfile` and rebuild - a known Harbor edge-case bug. If the task genuinely needs curl, flag it to the user for the Slack channel with the submission UID
- **DownloadVerifierDirError / verifier-output-not-found**: fix the upstream cause (bash vs ash shebang, missing artifact path, missing tmux or asciinema)
- **Linter rejects the task as "easy" after a difficulty downgrade**: a known platform issue. Do NOT hand-edit the pass-rate or difficulty fields in `task.toml` to satisfy a reviewer - the linter rejects anything it reads as easy, so matching the metadata to the measured difficulty and satisfying the linter pull in opposite directions. Never tweak the metadata back and forth; tell the user to flag it on Slack with the task/submission UID and the two conflicting values (the linter's difficulty floor vs the measured metadata). This is a tooling gap, not a task defect
- **Checking submission status**: `stb submissions list` from the CLI is the source of truth. The GUI lags and can make a task flicker in and out; if the CLI and GUI disagree or a submission is stuck, flag it on Slack with the submission UID
- **Infra/platform error, or blank feedback**: `DaytonaRateLimitError` / `ApiRateLimitError`, sandbox auth or connection errors, a one-off `NonZeroAgentExitCode`, and "No evaluation information available" are platform failures, NOT task defects. Do not mark the task Not Fixable over one, and do not burn a revision slot resubmitting blindly - blank feedback usually means the eval output never came through, not that the task failed. The tell is inconsistency: the same task passes on one run and errors on the next, or 1 of N trials fails while the rest are clean. Retry; if it persists, have the user flag it on Slack with the task/submission UID, the exact error, and whether it is intermittent. Check `stb submissions list` for where the task actually is. **Distinguish this from a reproducible failure that only looks like infra** - "0/8 valid trials - tests.patch did not apply" fails identically every run and is a real defect with a real fix (first bullet above)
- **"Review gate blocked at the agentic judge / difficulty screen": content-side, not infra.** The bullet above does not extend to this one, and reading it that way costs a round of doing nothing. `docs/faq.md` ("My eval says Review gate blocked at the agentic judge / difficulty screen") is explicit that in almost every case a review-gate block is a real result you need to act on. Get the "Agentic Judge Quality Report" field for a judge block, expand PR scope for a difficulty-screen block, and treat "Not run: difficulty screen" as expected rather than as a second failure. **The one infra case is a message that explicitly says "the difficulty screen failed with an infra error"** - a sandbox or platform crash where no verdict was produced, so retry it the same way as the bullet above. Nothing else on that line is infra, and a review-gate block is never a Not Fixable condition. **That carve-out is also a budget carve-out**: `docs/faq.md` says the counter increases only when a check runs and returns a result, so a crash producing no verdict costs nothing, while a block that DID come back with a result plausibly spent one of the four. That is a direct reading of the FAQ sentence rather than something measured here, and it rests on a second assumption the FAQ never states, that this cheap single-arm screen is one of the capped checks at all. `Difficulty checks remaining` on the submission settles both in one round
- **The task came back with `Invalid Difficulty` already on the validity question**: that is the four-check cap firing, not a defect and not a bounce. `docs/faq.md` says the platform changes the answer itself at the limit, returns the task to you once with the verdict on it, and expects it submitted again for review with nothing changed and the verdict left as set. Do not rewrite the bundle, do not restore your own verdict, do not spend a revision round on it, and leave the form answers alone too, since the instruction is to change nothing. It still reaches a human reviewer. Record it in `task.md`, which is not part of the submission. Full treatment in the budget section above

### The rubric-panel judge

**Two descriptions of the same check, and they disagree. Both are here on purpose:**

| Description | Status | What it says | How to use it |
|---|---|---|---|
| **15 numbered must-have criteria** (`Q1`..`Q15`), each tagged with a `criterion:` group, reported as `N/15 criteria pass` | **MEASURED - this is the current behaviour** (observed 2026-08-02 on `20260728_153118__jqno_equalsverifier__1166`) | A failing must-have criterion blocks the task on its own, whatever the axis scores say | This is what the report you receive will actually look like. Read the criterion numbers and the `judge:` justifications |
| **10 axes scored 1–5 across four rubrics**, with REMOVE / DISCUSS / OK verdicts driven by the two test axes | **OLDER Hub description** - still what `docs/tasking-guide.md` says, and the axis scores do still appear in reports | Only `test_coverage` and `test_faithfulness` flip the verdict | Keep applying it to the test axes. Do NOT read "only the test axes matter" as covering instruction quality |

Reconciled: the must-have criteria are an additional blocking layer on top of the axis logic, not a replacement for it. Two independent LLM judges (Claude Opus and GPT-5.5) read the instruction, tests, oracle, and task directory and score 10 axes (1–5) across four rubrics: instruction quality (realism, clarity, self-containedness, prescriptiveness), test quality (test_coverage, test_faithfulness), oracle quality (spec faithfulness, no gaming, robustness/reproducibility), packaging. Where they disagree by 2+ on an axis, a blinded adjudicator settles it.

**Among the axis scores, only the two test axes flip the verdict - but the must-have criteria flip it independently.** Verdict logic:

- **REMOVE** (fails): adjudicated score on either test axis ≤ 2.0, OR either judge scored an axis ≤ 2 with the failure matching one of the six essential patterns below
- **DISCUSS** (fails): any single judge scored either test axis ≤ 2, OR the adjudicated score on either axis is ≤ 3.0
- **FAILS REGARDLESS OF THE AXES**: any must-have criterion fails. `criterion: Instructions` items block on their own - jqno 1166 failed with `13/15 criteria pass` and clean test axes. Instruction leakage (Q10) and navigation hand-holding (Q9) are the two that have actually fired
- **OK** (passes): both test axes above 3.0, no judge at ≤ 2, AND zero failing must-have criteria

Practical bar, in the wording `docs/tasking-guide.md` now carries (Section 3 Run Evals, the note under the Quality Check verdict logic): the judges score the test suite on coverage and faithfulness 1 to 5. A final score **above 3** on both axes passes. A final of **3 or below** on either axis sends the task to needs-revision, and a single judge at **2 or below** on either axis trips that too. A final of **2 or below** on either axis is a hard fail. Aim comfortably above 3, because a task sitting right at 3 does not pass - do not ship borderline, fix it.

**The 4+ target this workspace works to is its own margin, not the platform's bar.** The Hub used to word the bar as "both judges need a solid 4+" and no longer does, so keep aiming there if you like the headroom, and never quote 4+ back to a reviewer or into an answer as a documented rule. The number that is documented is above 3.

- **Coverage (Instruction → Tests):** every stated requirement has a real enforcing assertion; a broken or stub solution must fail at least one test. Gaps = false positives
- **Faithfulness (Tests → Instruction):** every assertion maps to something stated or reasonably implied. Hidden requirements = false negatives

### Six auto-REMOVE patterns (never ship these)

| Pattern                       | What it looks like                                                                                                                                                                 |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Silent skip                   | `@pytest.mark.skip`, `skipif`, catching ImportError and setting the module to None - anything letting substantive tests silently not run. A missing dependency must FAIL, not skip |
| No CLI/entry-point invocation | Instruction asks for a CLI/service/script, but test.sh only runs pytest against library internals and never invokes the thing being built                                          |
| Pre-created artifact passes   | `path.exists()` / `is_file()` without content checks, so `touch`-ing the filename passes. Pair every existence check with a content/behavior assertion                             |
| Agent controls coverage       | Tests iterate over the agent's own output (loop over its JSON entries), letting the agent shrink the test surface. Enumerate expected items from the instruction/environment       |
| Fail-open                     | `if not output.exists(): return`, `try/except: pass`, assertions gated behind preconditions. A missing or malformed artifact must fail the suite                                   |
| Overreach                     | Enforcing names, formats, thresholds, paths, or conventions the instruction never states                                                                                           |

### Test-writing checklist

**Do:** map every imperative, named output field, named edge case, and named threshold to at least one assertion (build the bipartite mapping yourself first); test at the instruction's stated strictness ("all rows" means all rows, a named threshold means assert the threshold); include the regression test that reproduces the original failure (fails pre-patch, passes post-patch); keep tests deterministic (fixed seeds, no order/wall-clock/network dependence); commit fixtures and mock data into the verifier image; if a specific output format is required, state it in the instruction so the format assertions are faithful.

**Don't:** assert on source-code text (substring/keyword scans); embed verifier-only constants the agent can't derive (`EXPECTED_COUNT = 47`); compare against hidden golden files never foreshadowed; compute expected values from the agent's own output (circular); require exact error strings, JSON key orderings, whitespace, tolerances, or file paths unless the instruction or an existing convention fixes them; wrap test bodies in broad try/except - ever.

### The advisory axes still matter (reviewers read them)

- **Instruction axes:** reward instructions that read like a real ticket, fully specify success, reference only artifacts that exist in the repo, and state requirements not procedure. Detailed output schemas score well; ordered how-to steps, file localization hints ("the bug is in helpers/queue.py"), and pre-answered edge cases score badly. Two specific triggers the prescriptiveness checker flags: naming the library or built-in the agent should have chosen, and naming an internal implementation file or the current home of code being migrated
- **Oracle axes:** implement every requirement with correct logic; no gaming - no hardcoded answers, fabricated tool output, reading test-side ground truth, or fixture-specific shortcuts (e.g. treating `df['Date'].max()` as "today"); reproducible - seeded randomness, no live network calls, timeouts on subprocesses. Litmus test: "if the inputs were reshuffled within the spec, would this oracle still produce the right answer?"
- **Packaging:** one stray dev artifact shipping into the container (`__pycache__/`, `.DS_Store`, `.venv/`, `.pytest_cache/`, `.idea/`, `.vscode/`, swap files, `.ruff_cache/`, `node_modules/`) hard-caps the axis at 1, as does any solution leakage into agent-readable paths

### If the Quality Check fails

Download the report and read the per-axis justifications - they cite exact files, line ranges, and quoted instruction text. Keep instruction, tests, and oracle in lockstep, re-upload, and re-run the evals until the check passes (`docs/tasking-guide.md:343`).

**Reason-to-Fix.** The report names a `Reason:` or `reason:` string. Each one has a different fix and a different target file, and picking the wrong file is how a round gets spent moving a problem rather than closing it:

| Reason | What the judge is saying | The fix | Lands in |
|---|---|---|---|
| `coverage_gap` | A requirement the instruction states has no assertion that would fail if it were removed | **First check whether it describes the source PR, not your tests** (see below). If it is genuinely your gap, add or strengthen an assertion and re-run the hostile-delete gate against that exact requirement | `tests/tests.patch` - or `instruction.md`, when the instruction over-promised |
| `oracle_spec_gap` | The instruction promises behaviour the golden patch does not implement | **Almost always an instruction defect, not an oracle defect.** Narrow the instruction to what the PR actually does. Changing the oracle to satisfy a judge is reducing or replacing PR behaviour, which is an Invalid condition and not available to you (`learning/source-pr-cross-check.md`) | `instruction.md` |
| `overreach` | A test enforces a name, format, threshold, path or convention the instruction never states | Either state the requirement in the instruction or relax the assertion. Do not add the requirement to the instruction just to keep a test - only do it if the requirement is genuinely part of the task | `tests/tests.patch`, or `instruction.md` |
| `weak_check` | An assertion exists but cannot fail - an existence check with no content assertion, a fixture that cannot violate the constraint it names, a test iterating the agent's own output | Rebuild the fixture so a broken implementation actually fails it (Section 10.4), then prove it with the hostile-delete gate | `tests/tests.patch` |
| Instruction leakage or hand-holding (`criterion: Instructions`, Q9 / Q10) | The instruction leaks the strings the tests assert, or tells the agent where to look | Delete the navigation and the quoted assertions outright. There is no safe rephrasing of placement under Q9, and grep the tests before deleting a name so you do not trade this for a `test_faithfulness` failure | `instruction.md` (and its `problem_statement.md` copy) |

`overreach` and `weak_check` are **second-hand** - they are named in the rubric vocabulary and this workspace has not seen either in its own reports, so the fixes above are reasoned from the axis definitions rather than measured. `coverage_gap`, `oracle_spec_gap` and the Q9 / Q10 criteria have all fired on real rounds and are worked as cases in `learning/quality-check-criteria.md`.
