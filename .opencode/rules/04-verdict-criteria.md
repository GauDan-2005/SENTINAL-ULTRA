## 3. Verdict criteria (official)

**Valid as-is:** instruction, tests, and oracle all align with each other and with the source PR. No edits required. All 7 compliance items are genuinely true.

**Fixable** - any of:

1. Instructions overly prescriptive or exposing verifier internals
2. Instruction reads as templated/AI-generated
3. Tests miss requirements stated in the instruction
4. Tests grade undescribed behavior or rely on arbitrary (non-derivable) names
5. Fewer fail-to-pass tests than the bar → add tests to reach it (11–20; the static check rejects anything outside 10–20)
6. Solution leakage (PR URL in instruction, environment spoilers, test-gaming shortcuts)
7. Oracle does not implement the instruction
8. Task too easy → raise difficulty by expanding PR scope. Material for that expansion may be adapted from a later PR in the same repo when it is a RELATED one - `docs/faq.md`, "A task came back too easy - can I adapt a change from a related PR to add complexity?". Never pull from an unrelated PR, never lift a PR wholesale, and never change the scope or feature of the original PR. This sits inside the expansion-only rule and does not widen it
9. A specific, LISTED Dockerfile issue (allowed-fix table in sentinel-task-fixing)
10. A git-hygiene issue in the shipped repo (leaked history, remote, HEAD/base mismatch, reflog, oversized .git)
11. A `task.toml` problem measured against the Section 8 limits - a value out of range, `gpus` not 0, a missing or stripped `network_mode` block, an agent timeout too low for the runs, inaccurate `category` / `difficulty_explanation` / source URL
12. Packaging problems - `tests.patch` cut against the wrong base, a pre-existing test file left modified in the shipped tree (not one that `tests.patch` edits, which is allowed), stray dev artifacts, `solution.patch` instead of `golden.patch`, `problem_statement.md` out of sync with `instruction.md`

**"Too easy" is Fixable only while adding to the PR can still raise it, and that is a measurement, not a reading.** The Fixable row at `docs/guidelines.md:65` is written as a conditional, "Overall task is too easy - but you can raise difficulty by adding to the PR scope", so Fixable trigger 8 holds only as long as the second half is true. The whole verdict then turns on one empirical question: can difficulty be raised by ADDING to this PR. Answer it by prototyping the candidate levers and scoring each one, not by judging the PR from its diff, because a lever every honest implementation already satisfies moves nothing. When every lever measures zero, the only remaining route is to replace the PR with a harder one, which is **Unfixable - Difficulty** and not a Fixable task you have not tried hard enough on. Pick the bucket by what the fix would have to be: needing a different PR because this one cannot be made hard enough is the difficulty bucket (`docs/reviewer-rubric.md:29`), and needing a different PR because this one is the wrong shape, or because the environment is untouchable, is the structure bucket (`:28`). When the shortfall is small and a lever inside the PR still moves it, that is neither bucket, because the rubric scores it Minor and calls it difficulty drift (`:111`), which is Fixable trigger 8. Keep the numbers you measured: on Path C they are the submission (Section 2), because a Not Fixable verdict is graded on its explanation alone. Worked example in `learning/raising-difficulty-on-a-wrapper-task.md`, accepted 2026-08-11. **Do that prototyping before the upload rather than through the platform.** As of 2026-08-14 the difficulty check is a budget of four per review cycle (`docs/faq.md`, "Difficulty checks are now capped - what is Invalid Difficulty?"), so a check spent finding out whether a lever chosen by reasoning works is a quarter of the budget, and that follows from the cap by reasoning rather than from anything measured here. The measurements that find a real lever are the ones already written down: build implementations from `instruction.md` alone (`learning/implementation-control-is-the-lever-generator.md`), run the discriminate matrix (`learning/difficulty-levers-must-discriminate.md`), and split the instruction you already wrote into clauses and check each one is graded (`learning/probe-the-instruction-you-already-wrote.md`).

**Invalid/Not Fixable - two buckets, and they are tagged separately.** `docs/reviewer-rubric.md:25-31` splits Unfixable into **Unfixable - Structure** and **Unfixable - Difficulty**, and says in as many words that lumping them as "invalid" is what sends ECs into three or more unpaid revision loops on tasks that were never fixable (`:31`). Decide which bucket before writing a word of the explanation, because the Path C checkboxes cannot carry the distinction and the prose is the only thing that can (Section 2, Path C).

**Unfixable - Structure** - either of:

1. PR scope needs to be changed or reduced - the only path to validity is reducing or replacing the PR scope entirely. `docs/reviewer-rubric.md:28` words the same bucket as "the only fix is to change/reduce the source PR scope, or the environment has issues ECs are not allowed to touch"
2. Environment issues ECs cannot fix: tangled image/dependency build failures, an oracle timeout that bumping cannot resolve, an agent that genuinely cannot finish within the 7200 s ceiling, heavy external-network dependency, genuinely unrecoverable git corruption

**Unfixable - Difficulty** - the task is genuinely too easy or too hard and cannot be recalibrated without leaving the PR scope (`docs/reviewer-rubric.md:29`). This used to sit inside trigger 1 above, on `docs/guidelines.md:217`, "If the only way to make a task solvable, difficult enough, or valid is to reduce or replace the PR scope, the task is Not Fixable". That sentence still holds and difficult enough still sits on equal footing with solvable and valid. What changed is that the rubric gives the case its own name and its own tag, because pay and routing treat the two differently. A task that is only slightly under-difficult and IS raisable inside the PR scope is not this bucket at all: the rubric scores that Minor and calls it difficulty drift (`:111`), which is Fixable trigger 8. And the section below is the test the bucket itself still has to pass.

**NOT a Not Fixable condition - the verifier host cannot execute the software under test.** `docs/guidelines.md:66` makes Not Fixable exactly two categories and neither of them is this one; the closest, "Image/dependency build failures", is scoped by its own text to install errors and missing system libs, and it is about the **image** failing to build rather than the product failing to run. The rubric's two Unfixable buckets do not add it either: `docs/reviewer-rubric.md:28-29` is source-PR scope, an environment ECs may not touch, and difficulty. `docs/` is silent on cross-platform, macOS-only and hardware-dependent repositories: measured across the eight policy tabs, `Darwin`, `Apple`, `aarch64`, `hypervisor` and `cross-platform` do not appear at all and every occurrence of `macOS` is zip-command boilerplate about `__MACOSX/` and `.DS_Store`. Re-measured 2026-08-14 against the 2026-08-13 export, which added the Reviewer Rubric tab: the five terms still return zero everywhere, the new tab carries none of the six, and the export changed no line carrying `macos` in any case, so the conclusion stands unchanged. So concluding Not Fixable on that ground is an inference rather than a rule, and on the one task where it arose the inference was also **false**. elfuse 162 is a macOS Hypervisor.framework program graded on `ubuntu:24.04`; its syscall translation units compile behind a stand-in for the framework header and run under `qemu-user-static`, and the rebuilt behavioural suite was accepted. **Run the Step 2 item 11 ladder before this reaches a verdict** (`learning/platform-locked-repos-are-still-testable.md`). The same reasoning covers the softer version of the mistake, which is keeping the task Fixable but accepting source-text assertions because behaviour "cannot be observed here" - that is what `docs/guidelines.md:135` bans by name and what the judge returned REMOVE on in `learning/airgapped-means-no-egress-not-no-sockets.md`.

**NOT a Not Fixable condition - platform and infra failures.** A failed eval is only a verdict input when it is caused by the task. `DaytonaRateLimitError` / `ApiRateLimitError`, sandbox auth or connection errors, a one-off `NonZeroAgentExitCode`, and a run that returns blank feedback or "No evaluation information available" are all platform-side. **Infra and platform failures never make a task Unfixable.** The tell is inconsistency - the same task passes on one run and errors on another, or only 1 of N agent trials fails while the rest are clean. Retry rather than reworking; do not burn a revision slot resubmitting blindly; if it persists, tell the user to flag it on Slack with the task/submission UID, the exact error, and whether it is intermittent (that is what separates an outage from a real defect). Before concluding anything from a red eval, separate a platform failure from a task defect that merely looks like one - `tests.patch did not apply` after an agent edited the tests reproduces on every run and IS a task defect (see Section 4 and `learning/tests-patch-vs-agent-edits.md`).

**A review-gate block is the same kind of carve-out - it is not on the platform-side list.** `docs/faq.md`, "My eval says Review gate blocked at the agentic judge / difficulty screen - what does that mean?", says a block is in almost every case a real content-side result to act on. Blocked at the agentic judge means the judge returned a needs-work verdict, and the reasons are in the "Agentic Judge Quality Report" field on the submission, which is collapsed and marked optional, not in the one-line summary. Blocked at the difficulty screen means the screen found the task trivially easy, which is Fixable trigger 8 and not an outage. "Not run: difficulty screen" means the judge blocked first so the later stage never ran, which is expected rather than a second error. The one infra case is a message that explicitly says the difficulty screen failed with an infra error, and that one is retried like the errors above. None of these makes a task Not Fixable. If the same block repeats across different tasks, or several land in a short window with otherwise-clean checks, have the user flag it on Slack with the UIDs - a cluster is what points at a platform-side problem rather than at each task.

### Unfixable - Difficulty, and the test that has to pass before you reach for it

This bucket used to be carried as a limb of the PR-scope trigger, on `docs/guidelines.md:217`, and libcrux 1165 was accepted on exactly that reading. `docs/reviewer-rubric.md:29` now gives it its own name and its own tag, which changes the label and nothing at all about the evidence it needs. It is the most over-claimed verdict in this workspace and the near-miss is measured: **redisshake 1005 had the complete dossier at round 4 and was ACCEPTED on that round.** Four consecutive `FAIL EASY` screens, four different lever classes each measured at 0 of 4, sixteen independent implementations all passing, six further related PRs surveyed and rejected with measurements. Every leg LEDGER L21 asks for was held, and the conclusion was still wrong.

Two conditions sit in front of this bucket. Both are cheap and both would have caught it:

- **Did the source PR's own author get anything subtly wrong?** A place upstream got wrong is a trap, and a trap you found is one a weaker model can walk into. redisshake had **three**, all still on the project's default branch. libcrux had none, because its PR wraps existing functions. A PR with no such place is where a ceiling is structural; a PR with one is a task you have not finished measuring
- **Whose model produced the zeroes?** A local control run on a model newer than the ones the screen grades is a **ceiling, never a forecast** (LEDGER L35, L51). redisshake's own artifact showed gpt-5.5 losing seven graded assertions to a trap Opus 5 found in 16 of 16 local runs. Never write a Not Fixable recommendation whose evidence is a set of local all-pass numbers

Compare the two on `learning/when-fail-easy-is-not-not-fixable.md`, which carries the side-by-side. And note what kept the wrong conclusion free on redisshake: it stayed in `task.md` and was never written into an answer. **The verdict belongs to the submitter, so hand them the dossier and the reading, not a recommendation dressed as a finding.**

**Since 2026-08-14 there is a second way into this bucket and it is not yours.** `docs/faq.md`, "Difficulty checks are now capped - what is Invalid Difficulty?", gives a task **four difficulty checks**. Once four have run without passing, the platform classifies the task **Invalid Difficulty** itself and sends it to review as it stands. Before that date a task could cycle through the difficulty check with no limit. A check spends budget only when it runs and returns a result, so a submission that comes back before the check runs costs nothing and a technical issue that prevents a result costs nothing, and **a reviewer sending the task back restarts the count at zero**, which makes this a budget per review cycle rather than a limit on the task's whole life. It is not a rejection, it is not retroactive to tasks that closed earlier, and a human reviewer still reads it. **None of that moves your own verdict discipline.** The two conditions above still sit in front of the bucket, a local control is still a ceiling and never a forecast, and you still do not reach Unfixable - Difficulty yourself off a repeated `FAIL EASY`. What changed is that the platform now reaches a difficulty verdict of its own at the fourth check, whether or not you have reached one, and what you do when it does is in Section 2 under the analysis question: the task comes back once with that verdict already set and is resubmitted unchanged.

**Two names, and `docs/` nowhere says they are the same thing.** **Unfixable - Difficulty** is `docs/reviewer-rubric.md:29` vocabulary, a bucket the reviewer tags and that you carry in the first line of a Path C explanation because the form has no control for it (Section 2, Path C). **Invalid Difficulty** is a value the platform writes into the submitter form's validity question when the four checks are spent (`docs/faq.md`). The two describe a similar predicament and no line in `docs/` equates them, so do not write one where the other belongs and do not treat the platform's value as confirmation of the rubric bucket you argued for.

**redisshake 1005 sits at or past that cap and was accepted anyway.** Its record says the screen blocked four times and does not say how many difficulty checks ran in total, so the arc is at or past the four-check budget rather than exactly at it. It also closed before 2026-08-14 and the policy is not retroactive, so nothing about it was affected. The reading above is unchanged and only its cost is now bounded: what used to be an argument for keeping at it is an argument for demonstrating it inside four checks, which is why the lever measurement moves in front of the upload (the trigger 8 paragraph above).

Rules: a single Not Fixable condition overrides everything. Fixable requires every issue actually fixed - a Fixable verdict with unfixed issues is never allowed. Full detail: sentinel-task-check and sentinel-task-fixing.

The verdict above is yours. The threshold the bundle is then judged against is the reviewer's, and it is documented: one confirmed Major Pillar violation is Needs Revision on its own, and five or more Minor violations across the eleven Secondary Requirements is Needs Revision on systemic low quality, with one to four accepted plus coaching comments (`docs/reviewer-rubric.md:13-19`). Section 2 carries the pillars and the counting rule.
