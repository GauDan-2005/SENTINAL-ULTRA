Configuring this Android beacon library has grown into a mixed bag over the years: some options live in manifest declarations, some are static fields on `BeaconManager`, some are instance methods, others hang off `Beacon` or the parsers. Worse, changing any of them after ranging or monitoring has already started is unpredictable — it is poorly documented which changes take effect immediately, some quietly do nothing until the next scan cycle, and a few can crash. We want a single, coherent configuration surface that library users can reason about, that works cleanly from both Kotlin and Java, and that applies a group of changes as one transaction (stopping and restarting scanning when needed) so behavior is deterministic. This is the new configuration API targeted for 3.0; it should live in package `org.altbeacon.beacon` alongside the existing settings for now.

Please introduce a `Settings` type (a Kotlin data class is the intended shape) whose every field is optional/unset by default so an instance describes only a *delta* of what the caller wants to change. It must expose these configurable fields, matching the names used below exactly: `debug` (Boolean — true switches the library log level to debug, false to info; default false), `distanceModelUpdateUrl` (String; default is the empty string, meaning disabled), `scanPeriods`, `scanStrategy`, `longScanForcingEnabled` (Boolean; default false), plus `distanceCalculatorFactory`, `regionStatePersistenceEnabled` (default true), `hardwareEqualityEnforced` (default false), `regionExitPeriodMillis` (default 30000), `useTrackingCache` (default true), `maxTrackingAgeMillis` (default 10000), `manifestCheckingDisabled` (default false), `beaconSimulator`, and `rssiFilterImplClass`. Scan periods are described by a nested `Settings.ScanPeriods` value constructed positionally as `ScanPeriods(foregroundScanPeriodMillis, foregroundBetweenScanPeriodMillis, backgroundScanPeriodMillis, backgroundBetweenScanPeriodMillis)` and also usable via those named parameters; its defaults are foreground 1100, foreground-between 0, background 30000, background-between 0. Because Java callers cannot use Kotlin named/default arguments, also provide a fluent `Settings.Builder` whose `new Settings.Builder()` supports at least `setDebug(boolean)`, `setDistanceModelUpdateUrl(String)`, `setScanPeriods(ScanPeriods)`, `setScanStrategy(ScanStrategy)`, `setLongScanForcingEnabled(boolean)`, and `setScanStrategy(...)`, each returning the builder, terminated by `build()` which yields a `Settings`. Expose the library defaults through a `Settings.Defaults` singleton so callers (and Java, via `Settings.Defaults.INSTANCE`) can read values such as `Defaults.distanceModelUpdateUrl` and `Defaults.getScanPeriods().getBackgroundScanPeriodMillis()`.

The scan strategy replaces the old scattered scheduling flags with a small closed set of `Settings.ScanStrategy` implementations, each of which knows how to configure the manager and can be compared for equality so the library can detect an actual strategy change: `Settings.ForegroundServiceScanStrategy(notification, notificationId)` taking an Android `Notification` and an int id; `Settings.JobServiceScanStrategy(immediateJobId, periodicJobId, jobPersistenceEnabled)` (the default on Android 8+); `Settings.BackgroundServiceScanStrategy()`; and `Settings.IntentScanStrategy()`. Alongside this, add a `DistanceCalculatorFactory` interface in `org.altbeacon.beacon.distance` with a single method `getInstance(context: Context): DistanceCalculator`, provide a `ModelSpecificDistanceCalculatorFactory` as the default implementation (it should build a model-specific calculator using the active `distanceModelUpdateUrl`), and let callers supply their own factory through the `distanceCalculatorFactory` field.

Finally, wire three application methods onto `BeaconManager`: `adjustSettings(settings)` applies only the fields explicitly set on the passed `Settings`, leaving everything else at its current value (a delta merge); `replaceSettings(settings)` applies the set fields and resets every unset field to the library default; and `revertSettings()` returns all settings to their defaults. Applying settings must happen as one transaction — among other effects it pushes `debug`, `hardwareEqualityEnforced`, the scan periods, region-exit and region-state-persistence options through to the manager, updates the distance model update URL, and instantiates the distance calculator from the configured factory and installs it so that after a call the library's active distance calculator is an instance produced by that factory. In particular, calling `adjustSettings` with a `Settings` carrying `distanceModelUpdateUrl = "www.google.com"` must make `BeaconManager.getDistanceModelUpdateUrl()` return exactly `"www.google.com"`. Reading back the applied configuration is done through `beaconManager.getActiveSettings()` (`beaconManager.activeSettings` from Kotlin), which returns a resolved, fully-populated snapshot (a *copy*) of what is currently in force — its fields like `debug` and `getScanPeriods().getBackgroundScanPeriodMillis()` are readable but mutating the snapshot must not change live configuration. If a strategy change is requested while consumers are bound, the manager should unbind and rebind them so the new strategy takes effect. Note a couple of constraints: the existing static configuration methods must keep working for backward compatibility (nothing here should break them), and you must not modify the test files under `lib/src/test`.
