Code generation falls over on large-but-ordinary schemas. buffa 0.9's element-memory budget is charged per element on *struct size*, not on encoded bytes, and `FileDescriptorProto` structs are wide — so the 32 MiB default rejects descriptor sets from perfectly normal schemas of a few hundred `.proto` files, not pathological ones. Concretely: a 400-file schema producing a ~19.7 MB descriptor set through `connectrpc_build::Config` dies with `failed to decode FileDescriptorSet: element memory limit exceeded`, while under a 1 GiB budget the same schema generates fine.

The compiler's own output (protoc / `buf generate`, or a descriptor set a build points at) is not the untrusted wire input that this budget is meant to defend against. So the two codegen entry points that decode that output should decode under buffa 0.9.1's higher "tooling" budget (1 GiB) instead of the untrusted default, and should honor the same two overrides buffa's own plugins do. Runtime reflection is different — a reflection service may be fed descriptors by a peer — so it stays on the bounded untrusted default, but its over-budget error must stop reading like corruption.

buffa 0.9.1 exports the whole mechanism, so a connect-specific twin is unnecessary — delegation to it suffices. `buffa_codegen` provides `decode_request`, `tooling_decode_options`, and `decode_failure`, plus the constants `buffa_codegen::ELEMENT_MEMORY_LIMIT_OPT` (the plugin-option key) and `buffa_codegen::ELEMENT_MEMORY_LIMIT_ENV` (the env-var name). buffa provides `buffa::DEFAULT_ELEMENT_MEMORY_LIMIT` and `buffa::DecodeError` (variants `ElementMemoryLimitExceeded`, `UnexpectedEof`, etc.). `buffa = "0.9.1"` is a hard floor — `decode_request` and `tooling_decode_options` don't exist in 0.9.0 — so `buffa`, `buffa-types`, `buffa-codegen`, and `buffa-descriptor` must be at `0.9.1` in the workspace `Cargo.toml`.

What the fix should accomplish:

The plugin binary decodes `CodeGeneratorRequest`s from stdin. Currently it uses a decode path that does not apply element-memory configuration. It should instead decode through `buffa_codegen::decode_request`, which picks up the 1 GiB tooling bound and the `BUFFA_ELEMENT_MEMORY_LIMIT` env override, so that large schemas decode successfully.

The `generate` function's option parser runs after the decode has already consumed the `element_memory_limit` parameter from the plugin option string. Since `buffa_codegen::decode_request` reads and applies that option before decoding, it is a leftover at option-parse time — but the user who needed it must still pass it. The parser must accept and silently ignore any option whose key equals `buffa_codegen::ELEMENT_MEMORY_LIMIT_OPT`, rather than reaching the unknown-option arm with a rejection. The unknown-option error's supported-options list must also include `element_memory_limit=<bytes|unlimited>`, keyed by `buffa_codegen::ELEMENT_MEMORY_LIMIT_OPT`.

The `connectrpc-build` crate has no plugin parameter string, so its `FileDescriptorSet` decode should use `buffa_codegen::tooling_decode_options()` instead of `FileDescriptorSet::decode_from_slice`. When the decode fails, the error should wrap `buffa_codegen::decode_failure` output. When the failure is specifically `DecodeError::ElementMemoryLimitExceeded`, the message must additionally name the `BUFFA_ELEMENT_MEMORY_LIMIT` environment variable (via `buffa_codegen::ELEMENT_MEMORY_LIMIT_ENV`) as the remedy that applies in this context, explain that a `build script` has no plugin parameter string (so the plugin-option override can't be used), and point to the guide documentation with a URL containing `connectrpc/connect-rust`. Any other kind of decode failure (e.g. a truncated set) must not mention the env var or budget — a malformed input should not be presented as a budget problem. Because the build script reads `BUFFA_ELEMENT_MEMORY_LIMIT`, a `cargo:rerun-if-env-changed` directive for that variable (using `buffa_codegen::ELEMENT_MEMORY_LIMIT_ENV`) must be emitted alongside the other rebuild triggers — without it, cargo will not re-run the build when the variable changes or is unset.

Runtime reflection stays on the bounded untrusted default, but `ReflectionError` needs a new `ElementBudget` variant to distinguish over-budget descriptor sets from corrupt ones. Both `from_descriptor_set_bytes` and `add_descriptor_set_bytes` must return `ElementBudget` when decoding encounters `DecodeError::ElementMemoryLimitExceeded`. The variant's `Display` message must say the bytes are `well-formed` and that the schema is simply large. `From<buffa::DecodeError> for ReflectionError` must be implemented explicitly (not via `#[from]` derive): `ElementMemoryLimitExceeded` maps to `ElementBudget`, every other variant maps to `Decode`. The explicit implementation is necessary because `#[from]` derives a blanket mapping that would route all `DecodeError`s — including over-budget ones — to `Decode`, and any future `?` on a new decode path would silently undo the distinction.

Notes: exact literals the behavior is checked against — the phrase `build script`, the substring `connectrpc/connect-rust` in the guide URL, and the word `well-formed` in the reflection error — must appear verbatim. Don't modify any test files.
