Code generation falls over on large but ordinary schemas.

buffa charges its element-memory budget per element on struct size, not on encoded bytes, and descriptor structs are wide. The 32 MiB default is meant for untrusted wire input, so a perfectly normal 400-file schema (about 19.7 MB of descriptors) dies with `failed to decode FileDescriptorSet: element memory limit exceeded`. Raise the budget and the same schema generates, 1600 files out.

Those descriptors are the compiler's own output: protoc, `buf generate`, or a descriptor set the build pointed at. That is not hostile input, so both codegen entry points have to decode under a bound sized for compiler output. Keep the bound finite. A truncated or corrupt set must still fail with an error rather than eat memory.

Users already have two knobs. The plugin option `element_memory_limit=<bytes|unlimited>` is per plugin. The environment variable `BUFFA_ELEMENT_MEMORY_LIMIT` (a byte count or `unlimited`) covers every plugin in a `buf generate` run and is the only knob a build script can set. Both codegen entry points have to honour both knobs, in both directions: a low byte count must reject a schema the compiler-sized default would accept, and `unlimited` must admit a schema the 32 MiB default rejects. When both knobs are set on the plugin, the option wins. Accepting `element_memory_limit=` later as leftover text is not enough. The option is consumed before the request can be decoded, so by parse time it is leftover: accept it and carry on, and list `element_memory_limit=` among the supported options when something unknown is rejected. Today the leftover falls through to the unknown-option arm and fails the one person who needed it.

`connectrpc_build::Config` has no plugin parameter string, so the env var is the only override it can honour. Because the build reads that variable, cargo must be told to rerun when it changes. When a build-script decode fails on budget, the error must name `BUFFA_ELEMENT_MEMORY_LIMIT`, say that a `build script` has no plugin parameter string, and point at our guide with a URL containing `connectrpc/connect-rust`. Any other decode failure, a truncated set included, must still read as a decode failure and must not mention the budget or that variable.

Runtime reflection is different. A peer can feed a reflection service descriptors, so it stays on the untrusted default even if `BUFFA_ELEMENT_MEMORY_LIMIT` is `unlimited`. An over-budget set there currently looks like corruption. Report `ReflectionError::ElementBudget` from `from_descriptor_set_bytes` and `add_descriptor_set_bytes`, with a message that says the bytes are `well-formed` and the schema is simply large. Route `buffa::DecodeError` so an over-budget error becomes `ElementBudget` and every other decode error stays `Decode`.
