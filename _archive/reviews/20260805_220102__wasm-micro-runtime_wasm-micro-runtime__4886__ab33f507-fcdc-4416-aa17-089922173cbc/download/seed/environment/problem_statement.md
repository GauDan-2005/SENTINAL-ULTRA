The WebAssembly Micro Runtime (WAMR) currently exposes `wasm_runtime_malloc` for runtime allocations but provides no way to obtain memory with a caller-specified alignment. This task adds aligned allocation support to the EMS garbage-collector allocator and surfaces it through a new public runtime API, so that callers who need alignment guarantees (for example for SIMD data or hardware buffers) can request them directly. Refer to `core/shared/mem-alloc/ems/ems_gc_internal.h` for the memory-layout architecture that the implementation must follow.

When a caller invokes the new public function `wasm_runtime_aligned_alloc(unsigned int size, unsigned int alignment)`, declared in `core/iwasm/include/wasm_export.h` with the `WASM_RUNTIME_API_EXTERN` linkage and defined in `core/iwasm/common/wasm_memory.c`, they should receive a pointer to a block of at least `size` bytes whose address is a multiple of `alignment`, or `NULL` when the request cannot be satisfied. The behavior is expected to satisfy the following acceptance criteria.

1. Given a valid power-of-two alignment that is at least 8 bytes and no larger than the system page size (obtained via `os_getpagesize()`, typically 4 KB), and a `size` that is an integral multiple of that alignment, aligned allocation should succeed and the returned pointer should be aligned to the requested boundary. Alignment values below the minimum of 8 bytes (`GC_MIN_ALIGNMENT`) should be treated as 8 bytes rather than rejected.
2. When `alignment` is zero, the function should emit the warning `wasm_runtime_aligned_alloc with zero alignment` and return `NULL`.
3. When `size` is zero, the function should emit the warning `wasm_runtime_aligned_alloc with size zero` and then allocate at least `alignment` bytes (the smallest multiple of the alignment). When the runtime is built with `BH_ENABLE_GC_VERIFY` enabled, a zero size is treated as a fatal misuse and the process exits.
4. When the runtime is built with `WASM_ENABLE_FUZZ_TEST` enabled and `size` is greater than or equal to `WASM_MEM_ALLOC_MAX_SIZE`, the function should emit the warning `wasm_runtime_aligned_alloc with too large size` and return `NULL`.
5. Aligned allocation is only supported in POOL memory-allocator mode. In any other memory mode the request should fail and return `NULL`, and when memory has not been initialized the failure should be reported. An alignment that is not a power of two, or a `size` that is not an integral multiple of the alignment, or an alignment exceeding the page size, should all fail.
6. The allocator must be able to distinguish an aligned allocation from an ordinary one so that freeing and reallocation behave correctly. Internally the aligned block stores an offset and a magic marker in a small metadata header located immediately before the returned pointer; the offset occupies 4 bytes (`ALIGNED_ALLOC_OFFSET_SIZE`) and the magic occupies 4 bytes (`ALIGNED_ALLOC_MAGIC_SIZE`) for a total metadata size of 8 bytes (`ALIGNED_ALLOC_METADATA_SIZE`), with the magic value encoding the alignment (`ALIGNED_ALLOC_MAGIC_VALUE` masked by `ALIGNED_ALLOC_MAGIC_MASK`). A helper such as `gc_is_aligned_allocation` should recognize these blocks. Freeing an aligned pointer, freeing an already-freed pointer, and freeing read-only data should all be handled safely.
7. Reallocation must not be attempted on an aligned allocation, because realloc does not preserve alignment and doing so has undefined behavior. Both `wasm_runtime_realloc` and the underlying `gc_realloc_vo` path should reject an aligned block (logging `[GC_ERROR]gc_realloc_vo does not support aligned` and returning `NULL`) while ordinary reallocation of non-aligned blocks continues to work. The new GC entry points `gc_alloc_vo_aligned` / `gc_alloc_vo_aligned_internal` back the aligned path.

Between the public API and the GC, expose the aligned path at the memory-allocator layer as `mem_allocator_malloc_aligned(mem_allocator_t allocator, uint32 size, uint32 alignment)`, declared in `core/shared/mem-alloc/mem_alloc.h` alongside the existing `mem_allocator_malloc` / `mem_allocator_realloc` / `mem_allocator_free`. `wasm_runtime_aligned_alloc` calls it in POOL mode (forwarding to `gc_alloc_vo_aligned`), and the unit tests call `mem_allocator_malloc_aligned` directly to exercise the allocator without going through the runtime. Under `BH_ENABLE_GC_VERIFY` follow the same `_internal(..., file, line)` convention used by the other `mem_allocator_*` entry points.

Ordinary allocation via the existing path must continue to work unchanged, including large-size requests and allocation until out-of-memory, and mixed sequences that interleave ordinary and aligned allocations (including objects promoted to HMU) must remain consistent.

The verified behavior is exercised by C unit tests under `tests/unit/mem-alloc/` (`mem_alloc_test.c` driven by `test_runner.c` using the cmocka framework), registered through `tests/unit/mem-alloc/CMakeLists.txt` and added to the unit-test suite in `tests/unit/CMakeLists.txt` as the ctest targets `mem-alloc-test` and `mem-alloc-gc-test` (the latter compiled with `-DWAMR_BUILD_GC=1 -DWAMR_BUILD_GC_VERIFY=1`). All of these tests should pass. As part of this change, the obsolete `tests/unit/tid-allocator` test is removed from the suite, and the `bh_queue` test is adjusted to free the queues and messages it creates and to avoid touching read-only message bodies.
