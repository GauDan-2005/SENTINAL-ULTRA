What makes this task difficult?
The work is one feature spread over two screens that already exist and have to keep behaving exactly as they did. A click-region layer has to hand out ids that never collide between components, wrap parts of a view without changing a single visible character, and record where each marked region ended up on screen after lipgloss has composed panels, borders and a scrolling viewport around it, with each fresh scan replacing what the last one recorded. Then five call sites have to agree on how a click becomes an action, the picker, the operation list, the endpoint list, the detail form and the search box, each with its own focus and typing state to move. Two things catch people. The regions are only registered if every view goes out through ScanMouseZones, and the explorer draws a wide two panel layout and a narrow stacked one, so an implementation can get the model exactly right and still miss every click on a narrow terminal. And DetailForm draws one row per field for an argument whose type is an input object, with every one of those rows carrying the same argument name, so setArgEnabled, sitting right there in formitem.go, switches all of them at once. Reaching for it is the natural move and it is the wrong one. The author of the upstream change made exactly that mistake and a later pull request had to go back and fix it.
