What makes this task difficult?
The change turns a single controller URL into a managed set of endpoints that the SDK keeps up to date on its own, and the ripple reaches further than the first read suggests. Changing the signature of ziti_ctrl_init breaks every caller, including the two enrollment paths and the context wiring, and config loading has to flip in both directions at once. A config that used to be rejected now has to load, and one that used to load now has to be rejected. Failover is the harder half. A switch is only allowed once nothing else is in flight, so the in-flight counter has to be raised and lowered on the right side of the response callback, and a cancelled request carries a negative code as well and must not set a switch off. The request that failed still has to hand the same error code back to its own caller, so the recovery cannot quietly absorb the failure. Endpoint selection prefers endpoints believed online, marks the one that just failed as offline, and still has to make progress when nothing is believed online, which is easy to write as a loop that returns nothing at all. The counter is the part most likely to be got wrong, because the rule is not that a failed request moves the endpoint, it is that a failed request moves the endpoint only when nothing else is waiting on a reply. Get that backwards and two requests failing together will move twice. On top of all that the endpoint set is not static. The SDK has to ask the controller for its peers once it has a session and not before, only when the controller said it was part of a highly available cluster, and then rebuild its set from the addresses that come back while keeping the online state each one reports. Very little of this shows up in one file, and a version that gets the counter or the peer refresh wrong will look fine right up until a controller disappears.
