The OpenZiti C SDK currently assumes a single Ziti controller: an identity's configuration is loaded into a `ziti_config`, and the controller client is initialized from exactly one URL. That design does not survive a highly-available (HA) deployment, where an identity can be served by several interchangeable controller endpoints and any one of them may become unreachable at any moment. When the one controller the SDK latched onto goes away, every request simply fails and there is no way to fall back to a peer, even though other healthy controllers are known. We need the SDK to manage a *set* of controller endpoints and transparently fail over between them, so that an application stays connected as long as at least one controller is reachable.

Concretely, `ziti_ctrl_init` in `library/ziti_ctrl.c` (declared in `inc_internal/ziti_ctrl.h`) must stop taking a single `const char *url` and instead accept a list of endpoints — its signature becomes `int ziti_ctrl_init(uv_loop_t *loop, ziti_controller *ctrl, model_list *urls, tls_context *tls)`. The `ziti_controller` struct should hold the working set of endpoints (a `model_map endpoints` keyed by URL, alongside the currently selected `url`, an `active_reqs` in-flight request counter, and an `is_ha` flag) rather than owning a single heap-copied URL string. On init, populate the endpoint map from every URL in `urls`, pick one to start with, and initialize the underlying `tlsuv_http_t` client against it; if the list is empty the call must fail with `ZITI_INVALID_CONFIG` and log that there are no controller endpoints. All existing callers must be updated to build a one-element list where they used to pass a bare URL — this includes the enrollment paths in `library/ziti_enroll.c` (both `ziti_enroll` and the well-known-certs continuation) and the context wiring in `library/ziti.c`, where `ztx_get_controller` should now return the single embedded `&ztx->ctrl` and the old per-URL loop that built a `model_list` of controllers (and the associated `ztx->controllers` field in `inc_internal/zt_internal.h`) is removed. Config loading in `library/config.c` must treat the controller list as the source of truth: a config with neither a `controllers` list nor a legacy `controller_url` (`ztAPI`) is `ZITI_INVALID_CONFIG`, and when only the legacy `controller_url` is present it should be migrated into the `controllers` list. Correspondingly, `ziti_context_init` in `library/ziti.c` must accept a config that supplies controllers either way and only reject one that has neither.

The heart of the feature is failover behavior on the request path. Each started request increments `active_reqs`; each completed response decrements it. When a request comes back with a transport-level failure (a negative `r->code`), and it was the last outstanding request (`active_reqs` has dropped to zero), the controller should attempt to switch endpoints: choose the next endpoint, update both `ctrl->url` and the client via `tlsuv_http_set_url`, and log the switch — while a request that fails against an unreachable host still reports the error to its caller with code `CONTROLLER_UNAVAILABLE`. Endpoint selection should prefer endpoints currently believed online, mark an endpoint offline when it's the one that just failed, and fall back to any endpoint when none are known-online. The known endpoints are refreshed from the controller itself: after login and when fetching current edge routers, the SDK lists the HA controllers and rebuilds its endpoint map from each controller detail's `v1` edge `api_address`, preserving online/offline state; controller listing should only be issued when the controller advertised the HA capability (`is_ha`, derived from the version's `HA_CONTROLLER` capability via `ziti_ctrl_caps`). Logging of a controller should now include host and port (e.g. `ctrl[host:port]`), and controller cleanup in `ziti_ctrl_close` must free the endpoint map instead of a single URL string. Please keep the observable error contract intact — an initialized-but-unreachable controller must surface `CONTROLLER_UNAVAILABLE` to a version request's error callback — and do not modify the test files under `tests/`; they encode the acceptance criteria for this work.
