OpenWhispr supports bring-your-own-key (BYOK) workflows for a growing set of cloud LLM providers. Each provider's secret plumbing has historically lived in four separate places — the environment/secret store (`src/helpers/environment.js`), the IPC layer (`src/helpers/ipcHandlers.js`), the sandboxed renderer bridge (`preload.js`), and the settings store — with every provider requiring its own getter, setter, IPC channel, and store key duplicated across those locations. This duplication is prone to drift: adding OpenRouter as a first-class provider exposed how easily one of the four spots gets missed, resulting in a key that saves but never loads, or a renderer bridge pointing at a channel the main process never registered. Each BYOK provider's plumbing should be defined exactly once in a single manifest, and OpenRouter should be onboarded through that manifest as a first-class, independently-stored secret.

Requirements: introduce a single source of truth at `src/config/secretKeys.js` that exports a `BYOK_API_KEYS` array (CommonJS `module.exports = { BYOK_API_KEYS }`, so both the Electron main process and the Vite renderer can `require` it). Each entry describes one provider and must carry five non-empty fields — `base`, `env`, `get`, `save`, and `storeKey` — where `base` is the lowercase provider slug that yields the IPC channels `get-<base>-key` and `save-<base>-key`, `env` is the process environment variable holding the secret, `get`/`save` are the accessor method names, and `storeKey` is the persisted settings-store key. The `base`, `env`, and `storeKey` values must each be unique across the whole manifest (no two providers may collide on a slug, an env var, or a store key). The manifest must contain exactly eight BYOK providers, in this order: OpenAI, Anthropic, Gemini, Groq, xAI, Mistral, OpenRouter, and Tinfoil. The naming conventions for each provider's fields should be consistent with how the seven already-existing providers are named in the codebase — OpenRouter follows the same patterns.

The environment/secret manager in `src/helpers/environment.js` derives its per-key accessors from this manifest rather than declaring them by hand. For every entry, an `EnvironmentManager` instance exposes a working `get`-named method and `save`-named method, each a function. When the save method is called with a secret, that secret round-trips so the matching get method returns the same secret, and the secret is written to the provider's `env` environment variable. When the save method is called with an empty string, the secret is cleared so the get method returns `""` and the corresponding environment variable is removed (undefined) rather than left behind. The manifest's list of env vars continues to feed the manager's overall set of known secret keys alongside the non-BYOK secrets it already tracks.

The dictation overlay, notification, and transcription-preview windows run a sandboxed `preload.js` that cannot `require` a local module, so the provider bridges are inlined in a `BYOK_KEY_BRIDGES` array declared as `BYOK_KEY_BRIDGES = [ ... ];`. Each element is a `{ base, get, save }` tuple whose values exactly match the corresponding manifest entry, and the array contains one tuple per manifest entry — no extra bridges and none missing — keeping the renderer's exposed `get`/`save` functions in lockstep with the main-process channels (`get-<base>-key` / `save-<base>-key`). Every method name and IPC channel that existed before is preserved (generated, not renamed) so nothing downstream breaks.

The test files remain unchanged.
