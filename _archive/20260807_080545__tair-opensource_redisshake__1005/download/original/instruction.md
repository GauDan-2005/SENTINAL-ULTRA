RedisShake replicates cleanly from Redis 7.x and the classic RDB layout, but breaks against Redis 8.0 and Valkey 9.0 sources. Both added first-class hash-field expiration along with new hash and stream commands, and Valkey 9.0 changed how TTL-bearing hashes are stored on disk. As a result some of the new commands aren't routed for cluster slot calculation, and type-22 hash payloads from a Valkey source get decoded with the wrong reader. Add support for these sources across the sync, scan, RDB and AOF paths.

The command table needs to route the Redis 8 hash commands `HGETDEL`, `HGETEX` and `HSETEX`, each reporting its key at argument index 1 (group `HASH`) so cluster slot routing works. The legacy hash-field-TTL commands (`HEXPIRE`, `HEXPIREAT`, `HPEXPIRE`, `HPEXPIREAT`, `HTTL`, `HPTTL`, `HEXPIRETIME`, `HPEXPIRETIME`, `HPERSIST`) must stay registered, since they appear in live traffic and RDB hash-TTL rewrite emits `hpexpireat`. The new stream commands `XACKDEL` and `XDELEX` (group `STREAM`, key at argument index 1) should be recognized as well.

The harder part is RDB decoding. Redis 8 and Valkey 9 both use RDB type byte 22 for TTL-bearing hashes, but their on-disk layouts differ. Valkey 9.0 writes each entry as field, then value, then an 8-byte little-endian millisecond TTL. The decoder needs to distinguish between these formats; the source flavor is recoverable from the RDB/AOF magic string (`REDIS` versus `VALKEY`).

When the source is Valkey, decoding a type-22 hash should produce `del <key>`, then for each field in order: `hset <key> <field> <value>`, followed by `hpexpireat <key> <ms> fields 1 <field>` when that field carries a non-zero millisecond expiration. Fields with a zero TTL get only the `hset`; no expire command is emitted for them.
