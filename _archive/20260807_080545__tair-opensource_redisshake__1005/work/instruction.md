RedisShake replicates cleanly from Redis 7.x and the classic RDB layout, but breaks against Redis 8.0 and Valkey 9.0 sources. Both added first-class hash-field expiration along with new hash and stream commands, and Valkey 9.0 changed how TTL-bearing hashes are stored on disk. As a result some of the new commands aren't routed for cluster slot calculation, and a snapshot written by Valkey is turned away before any of it is read. Add support for both sources on the snapshot, append-only-file and scan paths.

The command table needs to route the Redis 8 hash commands `HGETDEL`, `HGETEX` and `HSETEX`, each reporting its key at argument index 1 (group `HASH`) so cluster slot routing works. The legacy hash-field-TTL commands (`HEXPIRE`, `HEXPIREAT`, `HPEXPIRE`, `HPEXPIREAT`, `HTTL`, `HPTTL`, `HEXPIRETIME`, `HPEXPIRETIME`, `HPERSIST`) must stay registered, since they appear in live traffic and RDB hash-TTL rewrite emits `hpexpireat`. The new stream commands `XACKDEL` and `XDELEX` (group `STREAM`, key at argument index 1) should be recognized as well.

A snapshot opens with a nine-byte header, the name of the flavor that wrote it followed by version digits filling out whatever is left of the nine. Only a header naming `REDIS` is accepted today, and a Valkey 9.0 file names `VALKEY` there instead. Both have to load, and everything else about reading a snapshot has to go on working unchanged, per-key expiry included.

An append-only file may begin with a snapshot rather than a command stream, and that check has to accept both names too. What follows is a stream of commands whose arguments are length prefixed, and one of those commands carries a raw snapshot value, so an argument is free to contain any byte at all including the pair that ends a line. Every argument has to come back whole, and the stream has to stay lined up for the command after it.

The scan path has no file to read a header from, so it has to ask. Add `ParseServerVersion` to the client package, taking the reply of an `INFO server` call and reporting whether the server that sent it is Valkey. A reply carrying no version of the server's own is not an answer and has to come back as an error, and a replica reporting the version of the server it follows does not count as one. The scan reader has to use that answer when it decodes what it dumps.

The harder part is decoding. Redis 8 and Valkey 9 both use RDB type byte 22 for TTL-bearing hashes, but their on-disk layouts differ. A Valkey body opens with the number of entries, and then writes each entry as field, then value, then an 8-byte little-endian millisecond expiry. Not every field expires, and the format says so with a reserved value rather than with zero, because zero is an ordinary timestamp that has already gone by. Redis 8.0 keeps its own layout behind that same type byte and must go on decoding the way it does now, so the reader has to tell the two apart.

A decoded Valkey hash rewrites into the same command stream every other hash decoder here already produces, with its fields in the order the file stores them. What is new is the expiry. A field that has one needs it restored too, with the same expire command the other TTL-bearing hash decoders here already emit, naming the single field it applies to, right after the field itself. A field the format marks as never expiring gets no expire command at all. A field that does carry one gets it replicated exactly as the file records it, even when that time has already gone by, so mistaking the never-expires marker for an ordinary expiry deletes a field that should have survived.

One more thing about these hashes. A single field can hold a value larger than the target will accept in one message, and a copy that meets one has to keep going rather than stopping there for good. That is worth checking rather than assuming, because a run that stalls this way never reports an error.
